# 기기 인증 운영 적용 준비 — 운영 적용·실제 브라우저 시험은 별도 승인

현재 후보는 보호 API의 기기 검증과 화면의 기기 연결을 즉시 강제한다. 첫 기기가 `approved`가 되기 전에는 로그인·기기 등록·상태 조회는 가능해도 보호 메모 조회·변경·복원이 잠긴다. 현재 후보를 바로 배포하는 방식은 안전한 무중단 배포 준비가 완료된 상태가 아니다. 아래의 등록 전용 선행 릴리스는 아직 구현하지 않았으며, 운영 DB 변경·릴리스 제작·배포·기기 승인·심판 제출은 이 문서만으로 승인되거나 실행되지 않는다.

[기기 요청 계약](DEVICE_REQUEST.md)은 별도 HTTP 구현이다. 공식 [판정기 계약](DECIDER_REQUEST.md)의 18개 입력·5개 응답과 `decide(request)`, 실제 구현한 `RULE_IDS`를 유지한다. `judgeIssuer`를 다른 발급자로 바꾸거나 심판 요청에 기기 검증 예외를 두지 않는다. 공식 엔진과 이 등록·서명 프로토콜의 호환성은 별도로 확인해야 한다.

## 일곱 단계 선행조건과 전환 순서

1. **독립 시험 환경에서 실제 인증장치를 확인한다.** 안정적인 별도 HTTPS origin을 정하고 그 origin/RP ID와 시험 Auth 발급자·PostgREST·DB를 함께 고정한다. 단순 DB 분리나 임의 preview URL만으로는 준비되지 않는다. 현재 운영 `publicAppUrl`을 유지한 preview 요청은 origin/RP 불일치로 거부된다. 운영 계정·키·쿠키·credential을 시험 환경에 복사하지 않는다. 실제 OS 사용자 확인(UV)과 `singleDevice`, BE=0·BS=0을 등록·서명 양쪽에서 확인한다. 동기화 가능한 passkey는 이 후보의 허용 조건에 맞지 않는다. 지원 OS·브라우저·인증장치 조합은 실측한 것만 기록한다. Vercel 시험 배포에서도 원시 path·query·body가 비동기 인증을 거친 뒤 보존되는지 확인하고, 같은 JSON 의미라도 바이트가 달라지면 거부되는지 시험한다. 객체만 남아 원시 바이트를 확인할 수 없다면 전환하지 않는다. 아래 일곱 브라우저 시나리오는 아직 실측 결과가 아닌 시험 계획이다.

2. **운영자 신원과 독립적인 지문 대조 경로를 마련한다.** 신뢰할 수 있는 DB 운영자 계정, 사용자 본인 확인 경로, 소유자·pending 기기·공개키 SHA-256 전체 64자리 소문자 16진수 지문을 대조할 비공개 절차가 필요하다. 첫 등록이거나 지문을 알고 있다는 이유만으로 승인하지 않는다. `service_role`·일반 API·브라우저에는 운영자 승인 권한을 부여하지 않는다. 근거가 부족하면 pending을 유지한다. 아래 운영자 절차와 매개변수 템플릿을 사용한다.

3. **추가 SQL만 별도 승인 후 적용한다.** 백업·복구 가능 여부와 기존 1~10단계 메모·정책 기준을 확인한 뒤, 의도한 운영 DB에 **신규** `supabase/step11-device-auth.sql`을 적용할 별도 승인을 받는다. 기존 SQL을 다시 적용하거나 기존 표·정책을 교체하지 않는다. 추가되는 비공개 표의 RLS, RPC/운영자 함수 권한, 소유자 경계와 활성 `pending`/`approved` 기기 10개 한도를 검증한다. 거부·회수·만료 이력은 감사 근거로 보존하며 삭제해 한도를 확보하지 않는다. SQL 적용만으로 업무 API의 강제 검증을 켜지 않는다.

4. **등록 전용 bootstrap 릴리스를 따로 제작·검토한다.** 기존 10단계의 로그인·메모 CRUD·복원 API와 화면을 그대로 제공하면서 기기 등록·상태 조회·서명된 승인 결정만 추가하는 선행 릴리스가 필요하다. 최종 릴리스와 **같은 운영 origin/RP ID**에서 사용해야 등록 credential을 이어 쓸 수 있다. 이 릴리스는 현재 미구현이며 추가 제작·배포 승인이 필요하다. 현재 강제 후보에 우회 환경변수나 검증 생략 플래그를 넣는 방식이 아니다. 별도 릴리스의 차이와 업무 기능 보존을 검토하고, 미승인 사용자도 기존 업무를 계속할 수 있는지 먼저 시험한다. 현재 강제 후보를 이 선행 릴리스 대신 배포하지 않는다.

5. **선행 릴리스에서 모든 활성 사용자의 승인 기기를 준비한다.** 별도 배포 승인 후 같은 운영 origin의 선행 릴리스에서 사용자가 로그인하여 **이 기기 등록**을 누르면 반드시 pending으로 등록되어야 한다. 독립적인 본인 확인과 전체 지문 대조를 마친 운영자만 첫 기기를 승인한다. 모든 활성 사용자가 실제로 쓸 수 있는 승인 기기를 확보했는지 확인하고, 승인된 첫 기기의 사용자 확인·서명된 결정으로 둘째 기기를 승인한다. 둘째 기기에서도 별도 pending 시험 기기를 거부하는 서명된 기기 결정을 검증한다. 선행 릴리스의 기존 업무 API 응답 성공을 요청 서명 검증 성공으로 취급하지 않는다. 자가 승인, 타 사용자 기기 결정, 사유 없는 결정은 거부되어야 한다. 미완료 사용자가 있으면 최종 강제 후보로 전환하지 않는다. 모든 승인이 회수되었거나 기기를 잃었으면 새 pending credential을 등록하고 동일한 독립 운영자 승인 절차를 다시 거친다. 예전 회수를 취소하거나 상태를 직접 되살리지 않는다.

6. **항상 검증하는 최종 후보를 별도로 확정한다.** 앞선 조건을 충족한 뒤에만 현재의 항상 강제되는 API·화면을 최종 후보로 검토한다. 그 후보의 `aleph.config.json`을 단계 11과 실제 승인된 배포 정보에 맞추고, `publicAppUrl`·로그인 발급자·허용 업무 경로·원본 API·복원 경로를 구현과 대조한다. 기기 상태나 역할을 공식 판정기 요청에 추가하지 않는다. 일반 `npm run build`로 Vercel 시스템 정보와 최종 커밋·단계·원점이 담긴 `/aleph.json`을 생성·확인한다. 운영 빌드에 `--local`을 넣지 않는다. 기존 9개에 devices 1개를 더한 후보 함수는 10개이며, 함수 수나 로컬 빌드 성공은 실제 브라우저·기기·Vercel 원시 요청 검증을 대신하지 않는다. 독립 시험 환경에서 아래 정상·거부 결과를 만족한 후보와 배포할 후보가 일치하는지 확인한다.

7. **전환·직접 점검·심판 제출을 각각 승인받는다.** 활성 사용자의 준비 증거와 복구 계획을 검토한 뒤 최종 강제 후보의 운영 전환 승인을 별도로 받는다. 전환 후에는 승인된 시험 자료만 사용해 정상 서명 요청과 미승인·변조·재사용·회수 요청의 거부를 확인한다. 저장점과 bundle 전에는 `src/attack-check.mjs`를 현재 자료실에 맞춰 검토한다. 현재 다섯 익명 점검만으로 기기 등록·승인·정상 서명·변조 거부·회수를 확인할 수 없으므로, 필요한 추가 직접 점검을 별도 승인 범위에서 수행하고 **실제로 보낸 요청의 결과만** 기록한다. 미실행 항목은 미실행으로 남기며 가상 시험·로컬 HTTP 결과를 운영 또는 심판 판정으로 쓰지 않는다. 커밋 대상과 비밀값 검사 결과를 먼저 확인하고 `bundle-notes.json`, `artifacts/submission.json`은 커밋하지 않는다. bundle 생성·심판 접수는 별도 승인 단계이며, 공식 엔진과 기기 프로토콜의 호환성을 확인하지 못하면 제출 준비 완료로 표시하지 않는다.

## 첫 기기 운영자 승인 절차

사용자가 같은 운영 origin에서 로그인하여 **이 기기 등록**을 누른 뒤 결과가 **승인 대기**인지 확인한다. 운영자는 비공개 DB에서 소유자·pending 기기·`public_key_sha256`을 확인하고 사용자에게서 별도 신뢰 경로로 확인한 전체 64자리 지문과 대조한다. 본인 확인 근거와 승인 사유를 함께 확보한다. 비밀번호·JWT·개인키를 사용자에게 요구하거나 전달받지 않는다.

신뢰 근거가 확보된 운영자만 `postgres` 권한으로 다음 **매개변수 템플릿**을 사용한다. API·브라우저·일반 서비스 역할에는 이 권한을 주지 않는다. 실제 소유자 ID·기기 ID·지문·사유는 공식 비공개 관리 화면에 입력하며 코드·로그·답변·Git·제출 묶음에 넣지 않는다.

```sql
-- 템플릿: 실제 값을 채우지 않은 상태에서는 실행할 수 없다.
select byteback_devices.operator_decide(
  :verified_owner_uuid, :pending_device_uuid, :independently_checked_fingerprint,
  'approved', :approval_reason
);
```

승인 후 사용자는 **기기 상태 새로 확인 → 승인 기기로 연결**을 누르고 인증장치에서 본인 확인한다. 서버 목록의 approved만으로 보호 자료가 표시되어서는 안 되며, 실제 서명 조회가 성공한 뒤에만 표시되어야 한다. 모든 승인 기기를 잃었을 때도 새 pending 기기와 이 절차를 사용한다. 최초 기기 자동 승인이나 심판·운영자 토큰의 검증 우회는 없다.

## 실제 브라우저 시험 일곱 시나리오 — 미실행

다음은 독립 시험 origin·시험 계정·가상 자료에서 수행할 절차다. 운영 데이터로 반복하지 않는다. DB 불변 확인은 비공개 읽기 전용 비교로 한다. 거부된 작업에서는 메모·백업·타 사용자 자료·허가하지 않은 기기 상태가 바뀌지 않아야 한다. 정상적인 challenge 발급·소모나 감사 이력 추가는 업무 데이터 변경과 구분한다. 결과에는 시나리오 이름·HTTP 상태·상태 전이·비교 성공 여부만 남기고, 쿠키·JWT·proof·assertion·개인키·실제 ID·지문·자료 본문을 출력하거나 화면 캡처·네트워크 내보내기에 포함하지 않는다.

1. **설치·로그인·등록과 접근 권한을 구분한다.** 최종 강제 후보를 연 새 브라우저 프로필에서 로그인하고, 지원되면 **앱 설치**를 누른다. 설치만으로 승인 상태나 메모 화면이 열리면 실패다. **이 기기 등록**을 누르고 OS 사용자 확인을 완료한다. 지원되는 BE=0·BS=0 기기는 pending 하나만 생겨야 하고 메모·백업은 바뀌지 않아야 한다. pending 상태에서는 연결과 자기 승인으로 자료 접근 권한을 얻을 수 없어야 한다.

2. **첫 승인과 실제 서명 조회를 확인한다.** 시험 운영자가 독립 본인 확인·소유자·전체 지문 대조 후 위 템플릿으로 pending 하나를 승인한다. 잘못된 소유자·지문으로 시도한 결정은 상태가 바뀌지 않아야 한다. 사용자는 **기기 상태 새로 확인 → 승인 기기로 연결**을 누르고 OS 본인 확인한다. 버튼을 누르기 전에는 메모가 없고, 서명 GET 성공 후에만 자기 자료가 보여야 한다. DB에서는 승인 대상 기기·허용한 nonce·감사 기록 외에 메모·타 사용자 상태가 바뀌지 않아야 한다.

3. **정상 CRUD·복원을 사용자 동작으로 수행한다.** 연결 후 시험 메모를 추가하고 **메모 새로 읽기**를 누른다. 카드의 **수정 → 기기 확인 후 수정 저장**, 다시 읽기, **복원할 항목 확인 → 확인한 한 건 복원**, 다시 읽기, **삭제 → 기기 확인 후 삭제**를 차례로 수행한다. 보호 요청마다 OS 확인과 유효한 증명이 필요하며, 변경 후에는 이전 목록이 숨겨지고 명시적인 새 조회 후 갱신되어야 한다. DB는 요청한 자기 메모 한 건과 해당 검증된 백업·감사 범위만 바뀌어야 하며 다른 자료는 그대로여야 한다.

4. **둘째 기기를 승인·거부한다.** 같은 origin의 둘째 실제 기기에서 로그인하고 **이 기기 등록**으로 pending을 만든다. 첫 승인 기기에서 기기를 선택하고 3~240자 사유를 입력한 뒤 **이 기기 승인**을 눌러 OS 확인한다. 둘째 기기가 **승인 기기로 연결**에 성공하는지 확인한다. 별도 pending 시험 기기에는 **이 기기 거부**를 사용한다. 자가 승인·다른 사용자의 기기·빈 사유 결정은 거부되고 대상 외 기기와 메모·백업이 그대로여야 한다. 상태 전이는 서명된 결정 한 건과 감사 이력으로만 확인한다.

5. **Vercel 원시 요청 변조와 재사용을 거부한다.** 시험 메모의 수정 저장 버튼으로 서명 요청을 시작한다. 승인된 시험 중계기가 요청을 메모리에만 유지하면서 path·query·body를 각각 바꾸거나 소모된 nonce를 재사용한다. 원시 본문은 빈 바이트, JSON `null`, 공백·키 순서가 다른 동등 JSON도 구분해 확인한다. 증명이 묶인 값과 달라진 요청은 거부되고 메모·백업·기기 승인 상태가 그대로여야 한다. 업무 계약상 유효하고 비동기 인증 후에도 바이트가 일치하는 원본 요청은 정상 처리되어야 한다. 증명과 일치해도 `null` 등 업무 계약에 맞지 않는 본문은 데이터 변경 없이 거부되어야 한다. 실제 헤더·증명을 복사해 문서나 콘솔에 남기지 않는다.

6. **사용자 확인 취소와 지원하지 않는 credential을 거부한다.** 연결 또는 수정 저장 버튼을 누른 뒤 OS 확인 창에서 취소한다. 보호 자료와 복원 계획이 숨겨지고 성공 표시가 없어야 하며 업무 DB는 그대로여야 한다. 사용자 동작 없이 보호 요청을 시작하는 시도도 새 challenge·업무 요청 없이 거부되어야 한다. 실제 시험 장치에서 BE 또는 BS가 켜진 credential의 등록·서명을 시도하면 거부되어야 하며 승인 기기가 생기거나 업무 자료가 바뀌어서는 안 된다. BE/BS 조건을 만족하는 장치의 새 버튼 클릭 재시도는 정상 동작해야 한다.

7. **회수·오프라인·재로그인·기기 상실을 확인한다.** 둘째 승인 기기에서 첫 기기의 사유를 입력하고 **이 기기 승인 취소**를 누른다. 첫 기기의 새 보호 요청은 거부되고 표시 중이던 자료·복원 계획은 거부 응답 또는 다음 상태 조회에서 사라져야 한다. 활성 화면의 조회 간격은 30초이며 창 복귀 시에도 확인한다. 별도로 오프라인 전환과 로그아웃을 수행하면 즉시 숨겨지고 늦게 도착한 응답으로 되살아나지 않아야 한다. 오프라인 재진입에는 공개 안내만 보여야 하고 Cache Storage에는 허용된 공개 파일만 있어야 한다. 연결·로그인·승인 기기 확인을 다시 거쳐야 자료를 읽을 수 있다. 모든 기기를 회수한 경우 새 pending과 독립 운영자 승인으로만 회복하며, 회수 상태·감사 기록을 되돌리거나 거부 요청으로 메모·백업을 바꾸지 않는다.

## 실패 시 복구와 보존

최종 전환 전에는 검증한 이전 릴리스와 설정·스키마 호환성을 확보한다. 강제 검증을 시작한 뒤에는 검증을 계속 강제하는 정상 후보로 되돌리는 방법을 우선 준비한다. 10단계로의 롤백은 기기 검증을 제거하는 보안 하향이므로 별도 명시 승인이 필요하며 자동 복구 경로로 사용하지 않는다. 복구가 불확실하면 검증을 임의로 풀지 않고 실패 원인과 영향을 알린다.

추가 표를 drop하거나 down migration을 실행하지 않는다. 기존 1~10단계 SQL·메모·백업·정책·감사 이력을 보존한다. 감사 기록 삭제, 거부·회수 기기 상태의 임의 승인 복원, 검증 우회 플래그로 문제를 숨기지 않는다. 활성 pending/approved 한도와 만료 nonce 운영 정리는 감사 보존 원칙 안에서 별도로 검토한다.

기기 승인과 PWA 설치는 서로 다르다. `attestationType: none`이므로 제조사 인증이나 하드웨어 비추출성을 확인했다는 뜻도 아니다. 회수는 새 요청을 차단하지만 이미 승인 검사를 마친 업무 요청을 원자적으로 취소하지는 못한다. 실제 브라우저·OS·인증장치, 최종 Vercel 배포의 원시 요청 전달, 운영 Supabase, 공식 심판 기기 프로토콜은 각각 검증 결과를 확보하기 전까지 미검증으로 남긴다.
